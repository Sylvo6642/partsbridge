# Decisions

Each decision: what was chosen and why. Newest at the bottom.

| # | Date | Decision | Why |
|---|---|---|---|
| D-001 | 2026-10-23 | New repo, fresh start (not built on top of rfq-quote-agent) | Clean story for the portfolio; different stack (Postgres + pgvector instead of MongoDB) |
| D-002 | 2026-10-23 | Small scope: one loop (paste → extract → match → quote → accept), 8 build days. PDF, email, photos, tax/currency are "later" | A first draft with 13 days and many features was too complicated. A finished small loop beats a half-built big one |
| D-003 | 2026-10-23 | Supabase (Postgres + pgvector + Auth), OpenAI gpt-4o-mini + text-embedding-3-small, FastAPI, Next.js | Free tiers; one database does tables, keyword search and vector search; small cheap models are enough and keep costs to a few dollars |
| D-004 | 2026-10-23 | **The AI never decides who can see what.** Login → server checks the token → database rules (RLS) filter rows. Tools get the user's identity from the server, never from the model | A model can be tricked by prompt injection. If it never holds the keys, a tricked model still can't leak another user's data |
| D-005 | 2026-10-23 | One account with a Buyer/Seller switch, seeded sample RFQs and a bot seller | A visitor can try the whole loop alone, without needing a second person |
| D-006 | 2026-10-23 | Every AI feature gets a test set and a score, saved in `docs/evals/` | "It works" is not a number. Scores show whether a change helped |
| D-007 | 2026-10-23 | All frontend design and review with the `impeccable` skill | Consistent, polished UI without spending build days on CSS |
| D-008 | 2026-10-23 | Fictional brands (Norvik, Kanto Seiko, Ferrum), real part-number conventions | All data must be synthetic, but matching should still be a real problem (each brand writes the same bearing differently: `6205-2RS1`, `6205DDU`, `6205-2RSR`) |
| D-009 | 2026-10-23 | Interchangeable parts share an `interchange_group` column instead of a separate cross-reference table | Simplest thing that lets `find_equivalent` work: "other parts in the same group" |
| D-010 | 2026-10-23 | Catalog generated by code with a fixed random seed; CSVs committed | Anyone can rebuild the exact same data, and eval scores stay comparable between days |
| D-011 | 2026-10-23 | Money as `Decimal` in Python and `numeric(12,2)` in Postgres, one currency (USD) | Floats round badly (0.1 + 0.2 ≠ 0.3). Quote totals must be exact |
| D-012 | 2026-10-23 | RLS on every table from Day 1. Parts and sellers are public read-only; offers (prices, stock) have no public policy | Supabase exposes tables to the browser. With RLS on and no policy, a table is closed by default |
| D-013 | 2026-10-23 | Structured outputs via the OpenAI Responses API (`responses.parse` with a Pydantic class), `temperature=0` | The answer always has the right shape and types, so code can rely on it; temperature 0 makes eval runs more repeatable |
| D-014 | 2026-10-23 | All OpenAI calls go through `app/ai/llm.py`, which logs tokens, cost, latency and prompt version to `llm_calls` | One place to swap models, measure cost and debug. Logging failures never break the feature |
| D-015 | 2026-10-23 | Prompts are versioned files (`extraction_v1.md`, …). Old versions stay, so any version can be re-scored | Prompt changes are code changes: they need history and a before/after number |
| D-016 | 2026-10-23 | Keep extraction prompt **v3** (29/30 across tuning + held-out vs 25/30 for v1). Never tune on the held-out set | Scores on the tuning set are optimistic; the held-out set is the honest check, and only stays honest if untouched |
